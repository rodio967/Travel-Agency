# Travel Agency - представительство турфирмы

Итоговый проект по БД. Информационная система зарубежного представительства.

**Стек:** Java 21, Spring Boot 3.5, Hibernate/JPA, PostgreSQL, Spring Security,
React + TypeScript + Vite + Material UI.

---

## Запуск

### Через Docker Compose

При запущенном Docker выполните из корня проекта, где лежит `docker-compose.yml`:

```bash
docker compose up --build -d --wait
```

Откройте [http://localhost:5173](http://localhost:5173). При первом запуске
доступен вход под `admin` / `admin`.

При необходимости задайте в `.env` в корне проекта
`DB_NAME`, `DB_USER`, `DB_PASSWORD`.

```bash
docker compose logs -f     # смотреть логи
docker compose down       # остановить сервисы
```

Данные PostgreSQL хранятся в томе `postgres_data`.

### Вручную

Приложение состоит из двух частей: **backend** (REST API на 8080) и **frontend**
(React-интерфейс на 5173). Для работы нужны оба.

#### Backend

1. Поднять PostgreSQL и создать БД:
   ```sql
   CREATE DATABASE travel_agency;
   CREATE USER travel_agency WITH PASSWORD 'travel_agency';
   GRANT ALL PRIVILEGES ON DATABASE travel_agency TO travel_agency;
   ```
2. Параметры подключения задаются в `src/main/resources/application.yml`
   (или через переменные окружения `DB_URL`, `DB_USER`, `DB_PASSWORD`).
3. Запустить:
   ```bash
   ./gradlew bootRun
   ```
   Hibernate сам создаст таблицы (`ddl-auto: update`), а скрипт `data.sql`
   накатит триггеры бизнес правил. При первом старте автоматически создаются
   права, системные роли и стартовый администратор.

API поднимается на `http://localhost:8080`.

#### Frontend

```bash
cd frontend
npm install
npm run dev
```
Интерфейс откроется на `http://localhost:5173` и обращается к API по адресу
`http://localhost:8080`. Бэкенд должен быть запущен.

### Доступ

При первом запуске создаётся администратор:

| Логин | Пароль |
|-------|--------|
| `admin` | `admin` |

(переопределяются переменными `BOOTSTRAP_ADMIN_USERNAME` /
`BOOTSTRAP_ADMIN_PASSWORD`).
Дальнейшие пользователи и роли заводятся через интерфейс.

## Что реализовано

### Модель данных

Иерархия туристов через `JOINED` наследование Hibernate:
- `Tourist` (абстрактный) - базовая сущность;
    - `RestTourist` - отдыхающий, с предпочитаемым типом экскурсий;
    - `ShopTourist` - едет за грузом, имеет лимит и предпочтения по грузу;
    - `Child` - ребёнок, привязан к родителю-туристу.

Остальные сущности: `TouristGroup`, `Flight`, `Hotel`, `HotelBooking`, `Visa`,
`ExcursionAgency`, `Excursion`, `ExcursionBooking`, `Cargo`,
`FinancialEntry` (доход/расход с категорией), и подсистема доступа -
`AppUser`, `Role`, `Permission`.

### Бизнес-правила (триггеры PostgreSQL)

Ключевые ограничения из задания реализованы триггерами в `data.sql`.

При нарушении API возвращает понятную ошибку `409 Conflict`.

### CRUD

Все сущности доступны через веб-интерфейс: список, создание, редактирование,
удаление.

### Отчёты - 15 запросов из задания

Доступны в разделе «Отчёты»:

1. Список туристов для таможни (по группе, всей или по категории)
2. Расселение по указанной гостинице (всего или по категории, за период)
3. Количество туристов за период (всего и по категории)
4. Сведения о конкретном туристе: визиты, гостиницы, экскурсии, грузы
5. Расселение по гостиницам с количеством номеров и людей за период
6. Туристы, заказавшие экскурсии за период
7. Самые популярные экскурсии и самые качественные агентства
8. Загрузка указанного рейса (мест, вес, объёмный вес)
9. Грузооборот склада за период (с разбивкой по типу самолётов)
10. Финансовый отчёт по группе - в целом и по категории туристов
11. Доходы/расходы за период по категориям
12. Виды отправляемого груза и их доли в грузопотоке
13. Рентабельность представительства
14. Доля отдыхающих (всего или за период)
15. Сведения о туристах рейса: группа, гостиницы, груз, маркировка


### Произвольный SQL

Раздел SQL - выполнение только `SELECT` запросов с табличным выводом
(под правом `RAW_SQL_EXEC`), с базовыми ограничениями для безопасности.

## Доступ и безопасность (ACL)

Аутентификация - **HTTP Basic** поверх stateless-сессий (сервер не хранит
состояние, каждый запрос проверяется заново). Пароли хранятся как BCrypt-хэши.

Авторизация - **на уровне permissions**, а не ролей. Каждый эндпоинт защищён
аннотацией вида `@PreAuthorize("hasAuthority('TOURIST_READ')")`. Модель:

- **`Permission`** - атомарное право (например, `TOURIST_READ`, `CARGO_WRITE`,
  `RAW_SQL_EXEC`). Фиксированный список из кода, создаётся при старте.
- **`Role`** - настраиваемый набор permissions (ADMIN / MANAGER / OPERATOR
  создаются автоматически, можно добавлять свои через UI).
- **`AppUser`** <--> `Role` <--> `Permission` - связи многие-ко-многим.

Так состав прав роли можно менять в рантайме через интерфейс, не трогая код,
изменения применяются при следующем запросе пользователя.
